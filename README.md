# ember — Lab 02: Біти не брешуть

Рівень: **Standard**. Тег: `lab-02`.

Процесор `ember` уміє `step`: бере байт з пам'яті, розбирає опкод масками й зсувами, виконує групи `0x0_` і `0x1_` з [ISA.uk.md](https://github.com/rmalkevy/Programming-Practice-Projects/blob/main/courses/programming-fundamentals/ISA.uk.md) і виставляє прапорці Z/N/C.

## Збірка й запуск

```
cmake -S . -B build
cmake --build build
./build/ember        # оболонка
./build/test_alu     # самоперевірка: ALU по всіх 65536 парах, decode, step
```

Збірка йде з `-Wall -Wextra -Wpedantic -Werror`.


## Команди

| Команда | Що робить |
| --- | --- |
| `set <addr> <byte> [byte...]` | записати байти починаючи з адреси |
| `get <addr>`, `dump <addr> [len]` | прочитати байт / шістнадцятковий дамп |
| `reg <a\|b> <0..255>` | покласти значення в регістр |
| `regs` | надрукувати `PC A B Z N C` |
| `step [n]` | виконати n інструкцій, кожну з трасуванням |
| `alu <op> <a> [b]` | ALU без процесора, для M1 |

Числа можна писати як `200`, `0xC8` або `0b11001000`.

## Які рядки ISA.uk.md реалізовані

Усі опкоди, розміри й вплив на прапорці взято з таблиці, нічого не вигадано. Розмір кожної інструкції тут 1, тож `PC` рухається рівно на 1.

| Опкод | Мнемоніка | Розмір | Прапорці | Статус |
| --- | --- | --- | --- | --- |
| `0x00` | `HALT` | 1 | — | є |
| `0x01` | `NOP` | 1 | — | є |
| `0x10` | `ADD A, B` | 1 | Z N C | є |
| `0x11` | `SUB A, B` | 1 | Z N C | є |
| `0x12` | `AND A, B` | 1 | Z N, C=0 | є |
| `0x13` | `OR A, B` | 1 | Z N, C=0 | є |
| `0x14` | `XOR A, B` | 1 | Z N, C=0 | є |
| `0x15` | `NOT A` | 1 | Z N, C=0 | є |
| `0x16` | `SHL A` | 1 | Z N C | є |
| `0x17` | `SHR A` | 1 | Z N C | є |
| `0x18` | `INC A` | 1 | Z N (C не чіпає) | є |
| `0x19` | `DEC A` | 1 | Z N (C не чіпає) | є |

Решта таблиці (`OUT`, `CMP`, `MUL`, `LOADI`, стрибки тощо) чекає своїх лаб. Невідомий опкод поки діє як `NOP` на один байт; у Lab 4 це стане помилкою.

**Власні розширення опкодів:** немає. Додано лише допоміжні речі, які не є інструкціями: команди оболонки `alu` і `regs`, функції `decode()` та `mnemonic()`.

## Розбір опкода масками

Старший півбайт опкода — це група, тому `decode` не тримає таблицю магічних чисел:

```cpp
Decoded decode(Byte op) {
    d.group = (op >> 4) & 0x0F;   // 0x1_ -> ALU
    d.index =  op       & 0x0F;
}
```

`step()` розводить `switch` за `decode(op).group`: група `0x0` іде в керування, група `0x1` у `exec_alu`.

## Розібрані приклади: загортання і перенесення

**1. `200 + 100`.** 200 = `1100 1000`, 100 = `0110 0100`. Сума 300 = 256 + 44 не влізла у вісім бітів: молодші вісім дають `0010 1100` = 44, а дев'ятий біт виїхав у `C`.

```
alu add 200 100   ->   result=44  Z=0 N=0 C=1
```

**2. `5 - 10` (позика).** Менше віднімають від більшого, тож результат загортається: 5 − 10 = −5 ≡ 251 (`1111 1011`). Старший біт одиниця, тому `N=1`; позика виставляє `C=1`.

```
alu sub 5 10      ->   result=251  Z=0 N=1 C=1
```

Ще два випадки, які перевіряє `alu`:

```
alu add 255 1     ->   result=0    Z=1 N=0 C=1     (загортання в нуль)
alu shl 129       ->   result=2    Z=0 N=0 C=1     (біт 7 виїхав у C)
```

## Трасування

Формат кожного кроку: рядок `адреса: байт мнемоніка` і нові регістри після нього.

**M2: `ADD`, `HALT` при `A=200`, `B=100`** (байти `10 00` покладено через `set 0 0x10 0x00`):

```
0000: 10  ADD A, B
PC=0x0001  A=44 (0x2c)  B=100 (0x64)  Z=0 N=0 C=1
0001: 00  HALT
PC=0x0002  A=44 (0x2c)  B=100 (0x64)  Z=0 N=0 C=1
halted                      <- третій step відмовляє
```

**M3: `AND`, `HALT` при `A=7`, `B=1`:**

```
0000: 12  AND A, B
PC=0x0001  A=1 (0x01)  B=1 (0x01)  Z=0 N=0 C=0
0001: 00  HALT
PC=0x0002  A=1 (0x01)  B=1 (0x01)  Z=0 N=0 C=0
```

Маска `7 & 1` лишає тільки молодший біт, а `C` скинуто, бо `AND` завжди пише `C=0`.

**M3: `SHL` тричі, потім `HALT` при `A=0x30`** (байти `16 16 16 00`). Біт `0011 0000` їде вгору, поки не вилізе за край:

```
0000: 16  SHL A
PC=0x0001  A=96 (0x60)   B=0 (0x00)  Z=0 N=0 C=0
0001: 16  SHL A
PC=0x0002  A=192 (0xc0)  B=0 (0x00)  Z=0 N=1 C=0      <- старший біт став 1: N
0002: 16  SHL A
PC=0x0003  A=128 (0x80)  B=0 (0x00)  Z=0 N=1 C=1      <- біт виїхав за межу: C
0003: 00  HALT
PC=0x0004  A=128 (0x80)  B=0 (0x00)  Z=0 N=1 C=1
```

**`INC` не чіпає `C`:** `ADD` при `A=255`, `B=1` дає `A=0`, `Z=1`, `C=1`; наступний `INC` робить `A=1`, `Z=0`, але `C` лишається 1:

```
0000: 10  ADD A, B
PC=0x0001  A=0 (0x00)  B=1 (0x01)  Z=1 N=0 C=1
0001: 18  INC A
PC=0x0002  A=1 (0x01)  B=1 (0x01)  Z=0 N=0 C=1
```

## Баг із пріоритетом, який я показав навмисно

`==` зв'язує тісніше за `&`, тому `x & 1 == 0` — це `x & (1 == 0)`, тобто `x & 0`. З `-Werror` це навіть не збирається:

```
error: suggest parentheses around comparison in operand of '&' [-Werror=parentheses]
```

Без `-Werror` при `x = 2` вийшло:

```
x & 1 == 0      ->  0      (це 2 & 0)
(x & 1) == 0    ->  1      (2 парне)
```

Тому скрізь, де потрібна перевірка біта, стоять дужки: `(flags & mask) != 0`.

## Самоперевірка

`test_alu` порівнює кожну операцію ALU з еталонною арифметикою у ширших типах для всіх 65536 пар `(a, b)`. Для кожної пари перевіряються значення й три прапорці. Окремо перевірені `decode(0xA3)`, `step` з `HALT` (наступні `step` не рухають `PC`), `INC`/`DEC` із збереженням `C` і невідомий опкод.
