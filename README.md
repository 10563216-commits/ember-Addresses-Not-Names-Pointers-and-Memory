# ember — Lab 03: Адреси, а не імена

Рівень: **Standard**. Тег: `lab-03`.

У Lab 2 процесор умів рахувати над регістрами. Тепер він уміє **діставати до пам'яті**: `LOADI`, `LOAD`/`STORE` за адресою, адресний регістр `H`, `OUT`/`OUTN` і команда `run`. Код живе з `0x000`, дані з `0x800`, інструкції й дані лежать в одній коробці (машина фон Неймана). Усі опкоди й розміри беру з [ISA.uk.md](https://github.com/rmalkevy/Programming-Practice-Projects/blob/main/courses/programming-fundamentals/ISA.uk.md), нічого не вигадано.

Усі інструкції групи `0x2_` **не чіпають прапорці**: завантаження нуля в `A` не виставляє `Z` (ISA.uk.md §3). Це перевіряє `test_flags_untouched`.

**Власні розширення опкодів:** немає. Додано лише допоміжні речі, які не є інструкціями: команди оболонки `set16`, `get16`, `run`, `reg h`; функції `instr_size()`, `disasm()` і `run()`.

## M1 — порядок байтів, молодший уперед

`get16` дано, `set16` написано як його дзеркало: молодший байт іде за адресою `addr`, старший за `addr + 1`.

```cpp
std::uint16_t get16(const Memory& mem, std::size_t addr) {   // ДАНО
    Byte lo = mem_get(mem, addr);
    Byte hi = mem_get(mem, addr + 1);
    return (std::uint16_t)(lo | (hi << 8));
}

bool set16(Memory& mem, std::size_t addr, std::uint16_t value) {   // моє дзеркало
    if (addr >= (std::size_t)MEM_SIZE - 1) return false;
    mem_set(mem, (std::uint16_t)addr,       (Byte)(value & 0xFF));   // молодший
    mem_set(mem, (std::uint16_t)(addr + 1), (Byte)(value >> 8));     // старший
    return true;
}
```

`value & 0xFF` лишає молодші вісім бітів, `value >> 8` пересуває старші вісім на їхнє місце: це Lab 2 у дії. Перевірку меж записано як `addr >= MEM_SIZE - 1`, а не `addr + 1 >= MEM_SIZE`: у другому варіанті `addr == SIZE_MAX` загорнувся б у 0 і пройшов перевірку. Якщо двох байтів немає, `set16` не пише **нічого** (не лишає напівзапису).

**Дамп порядку байтів:**

```
ember> set16 0 0x1234
ember> dump 0 2
0000: 34 12
ember> get16 0
1234
ember> get 0
34
ember> get 1
12
ember> set16 0xFFF 0x1234
error: set16 at 4095: needs addr and addr+1 inside 0x000..0xFFF
```

`0x1234` лягло як `34 12`: на меншій адресі молодший байт. Саме так лежить кожен 16-бітний операнд у потоці інструкцій (ISA.uk.md §4): `LOADH H, 0x0A00` збирається в `28 00 0A`, а `LOAD A, [0x0800]` у `22 00 08`.

`get16` у даному вигляді межі не перевіряє: `mem_get` маскує адресу до 12 біт, тож `get16(0xFFF)` мовчки прочитав би старший байт з адреси 0. Тому межі стереже той, хто викликає: `step()` і команда `get16` в оболонці.

## M2 — група `0x2_`, `OUT`/`OUTN`, `run`

`step` виконує інструкцію в такому порядку: прочитати опкод за `PC` → дізнатися розмір з `instr_size` → переконатися, що **всі** байти інструкції в пам'яті → виконати → `PC += розмір`. Безпосередній операнд `LOADI` лежить за адресою `PC + 1`; 16-бітний операнд читається через `get16` (молодший байт перший).

**Помилки замість загортання.** `PC` і `H` — це 16-бітні числа, а пам'ять має 4096 комірок, тож числа бувають поза коробкою. Усе, що тягне до адреси `>= MEM_SIZE`, зупиняє машину з повідомленням, і `PC` **лишається** на інструкції, яка помилилась:

```
ember> set 0 0x22 0x00 0x10 0x00        <- LOAD A, [0x1000]; HALT
ember> reg a 7
ember> run
-- error: LOAD at 0x1000: address out of range (valid 0x000..0xFFF)  (1 steps)
ember> regs
PC=0x0000  A=7 (0x07)  B=0 (0x00)  H=0x0000  Z=0 N=0 C=0
```

`A` не змінився й нічого не загорнулось у комірку `0x000`. Те саме з `H`: `INCH` на `0xFFFF` загортається в `0` (регістр 16-бітний, це не помилка), а помилка настає, коли за таким `H` **йдуть** (`LOAD A, [H]`, `STORE [H], A`). Ще дві межі: `PC >= MEM_SIZE` (програма пробігла за останню комірку) і триб'айтова інструкція на `0xFFE` або двобайтова на `0xFFF`, чий операнд виліз би за межу. Усе це зафіксовано в `test_faults`.

Після помилки машина зупинена: `step` і `run` лише повторюють повідомлення.

`run` крокує до `HALT` або до помилки. Окремої «стелі» на кількість кроків немає: без стрибків (Lab 4) `PC` тільки росте, тож програма скінчиться не пізніше ніж за `MEM_SIZE` кроків. Коли з'являться стрибки, стеля знадобиться.

## M3 — код на `0x000`, дані на `0x800`

Дані: `65 66 67 0` на `0x800` (рядок `ABC`). Код лежить в іншому регіоні тієї самої коробки.

### Варіант 1 — за абсолютною адресою

Програма: `LOAD A, [0x0800]` (`22 00 08`), `OUT` (`02`), `HALT` (`00`).

```
ember> set 0x800 65 66 67 0
ember> set 0 0x22 0x00 0x08 0x02 0x00
ember> run trace
0000: 22 00 08  LOAD A, [0x0800]
PC=0x0003  A=65 (0x41)  B=0 (0x00)  H=0x0000  Z=0 N=0 C=0
0003: 02  OUT
A
PC=0x0004  A=65 (0x41)  B=0 (0x00)  H=0x0000  Z=0 N=0 C=0
0004: 00  HALT
PC=0x0005  A=65 (0x41)  B=0 (0x00)  H=0x0000  Z=0 N=0 C=0
-- halted, 3 steps
```

Рядок, де надрукувалась літера, окремий: це `A` між трасуванням `OUT` і регістрами. Без трасування вивід коротший:

```
ember> run
A
-- halted, 3 steps
```

Дамп обох регіонів після запуску:

```
ember> dump 0 8
0000: 22 00 08 02 00 00 00 00
ember> dump 0x800 4
0800: 41 42 43 00
```

Код (`22 00 08 02 00`) і дані (`41 42 43 00`) лежать в одній коробці на різних адресах. `LOAD` знайшов дані, бо адреса `0x0800` вшита в сам код, молодшим байтом уперед: `00 08`.

### Варіант 2 — через `H`

Програма з семи інструкцій: `LOADH H, 0x0800` (`28 00 08`), `LOAD A, [H]` (`29`), `OUT` (`02`), `INCH` (`2B`), `LOAD A, [H]` (`29`), `OUT` (`02`), `HALT` (`00`).

```
ember> set 0x800 65 66 67 0
ember> set 0 0x28 0x00 0x08 0x29 0x02 0x2B 0x29 0x02 0x00
ember> run trace
0000: 28 00 08  LOADH H, 0x0800
PC=0x0003  A=0 (0x00)  B=0 (0x00)  H=0x0800  Z=0 N=0 C=0
0003: 29  LOAD A, [H]
PC=0x0004  A=65 (0x41)  B=0 (0x00)  H=0x0800  Z=0 N=0 C=0
0004: 02  OUT
A
PC=0x0005  A=65 (0x41)  B=0 (0x00)  H=0x0800  Z=0 N=0 C=0
0005: 2b  INCH
PC=0x0006  A=65 (0x41)  B=0 (0x00)  H=0x0801  Z=0 N=0 C=0
0006: 29  LOAD A, [H]
PC=0x0007  A=66 (0x42)  B=0 (0x00)  H=0x0801  Z=0 N=0 C=0
0007: 02  OUT
B
PC=0x0008  A=66 (0x42)  B=0 (0x00)  H=0x0801  Z=0 N=0 C=0
0008: 00  HALT
PC=0x0009  A=66 (0x42)  B=0 (0x00)  H=0x0801  Z=0 N=0 C=0
-- halted, 7 steps
```

Надруковано `A`, потім `B`, тобто `AB`. Зверніть увагу на колонку `H`: `LOADH` кладе в неї `0x0800`, `INCH` робить `0x0801`, і другий `LOAD A, [H]` приносить уже наступний байт. `A` і `B` тримають числа, `H` тримає **де**. У C++ це:

```cpp
Byte* p = &mem.bytes[0x800];   // LOADH H, 0x0800
Byte a = *p;                   // LOAD A, [H]   — *p
++p;                           // INCH          — ++p
a = *p;                        // LOAD A, [H]
```

`INCH` рухає `H` на **один** байт, бо комірка `ember` — один байт. `int*` у C++ при `p + 1` перестрибнув би чотири: арифметика вказівників рахує елементи, а тут елемент — байт. У Lab 4 ці сім рядків стануть циклом.

## M4 — вказівник хоста проти адреси гостя

**Чому `CPU` тримає `Memory*`, а `pc` і `h` — це `uint16_t`.** У програмі є два сорти «адрес», і їх не можна плутати.

*Вказівник хоста* — це `Memory* mem` у `CPU`: адреса всієї коробки в пам'яті мого C++-процесу. Вона потрібна одному місцю: тому, чим мій C++ розмовляє з масивом `bytes`. Вона змінюється від запуску до запуску (ASLR), займає 8 байтів, а після копіювання `Memory` вказувала б на стару копію.

*Адреса гостя* — це число `0x000..0xFFF`, яке бачить програма всередині `ember`. Саме такими є `PC`, `H` і операнди `LOAD`/`STORE`. Це індекс у `bytes`: на будь-якому запуску й на будь-якій машині `0x0800` означає той самий регіон даних. Його можна покласти в пам'ять (`LOADH`, а згодом `PUSH H`), надрукувати в дампі, порахувати в програмі-госте, і воно ніде не втрачає змісту.

Тому `pc` і `h` не `Byte*`: (1) індекс можна **перевірити** на `< MEM_SIZE` до того, як з ним щось робити (це робить `addr_ok` у `cpu.cpp`), а голий `Byte*` сам не знає, чи він іще всередині коробки; (2) 16-бітний регістр не вмістив би 64-бітний вказівник хоста; (3) програма-гість, що рахує з `H`, не залежить від того, де ОС поклала мій процес.

Баг, до якого призводить змішування: покласти вказівник хоста в пам'ять гостя або в `H` і чекати, що він щось означає. Від 64-бітного `0x7ffd26e0df40` лишиться молодші 16 бітів `0xDF40`, а це далеко за `0xFFF`: без перевірки меж `bytes[0xDF40]` — це запис у чужу пам'ять хоста, рівно те, що ловить ASan нижче. У зворотний бік: використати адресу гостя `0x0800` як вказівник хоста (`*(Byte*)0x800`) означає звернутися до неіснуючої сторінки процесу й упасти. Тому гість бачить тільки числа-індекси, а перетворення «індекс → `bytes[index]`» відбувається в одному місці й **після** перевірки меж.

**Навмисний вихід за межу.** Тимчасова програма (прибрана після цього):

```cpp
#include "memory.hpp"
int main(int argc, char**) {
    Memory mem;
    mem.bytes[MEM_SIZE + argc - 1] = 1;   // індекс 4096: допустимі лише 0..4095
    return mem.bytes[0];
}
```

`argc` потрібен, щоб компілятор не побачив індекс на етапі компіляції. Збірка: `g++ -std=c++17 -g -O0 -fsanitize=address -fno-omit-frame-pointer asan_demo.cpp memory.cpp`. Звіт згенеровано на Linux (g++ 13.3.0), початок і кінець зі списку байтів тіні пропущено:

```
==396==ERROR: AddressSanitizer: stack-buffer-overflow on address 0x7fed5da01020 at pc 0x5650e84023f6 bp 0x7ffd26e0df50 sp 0x7ffd26e0df40
WRITE of size 1 at 0x7fed5da01020 thread T0
    #0 0x5650e84023f5 in main /tmp/scratch/asan_demo.cpp:4
    #1 0x7fed5f42a1c9  (/lib/x86_64-linux-gnu/libc.so.6+0x2a1c9)
    ...

Address 0x7fed5da01020 is located in stack of thread T0 at offset 4128 in frame
    #0 0x5650e8402278 in main /tmp/scratch/asan_demo.cpp:2

  This frame has 1 object(s):
    [32, 4128) 'mem' (line 3) <== Memory access at offset 4128 overflows this variable
SUMMARY: AddressSanitizer: stack-buffer-overflow /tmp/scratch/asan_demo.cpp:4 in main
```

Три рядки, що мають значення: **(1)** `ERROR: ... stack-buffer-overflow`: який саме тип помилки; **(2)** `WRITE of size 1 ... asan_demo.cpp:4`: що робили (запис одного байта) і в якому рядку; **(3)** `[32, 4128) 'mem' ... offset 4128 overflows`: чия це межа. Об'єкт `mem` займає `[32, 4128)`, тобто рівно 4096 байтів, а запис потрапив на зміщення `4128`, на байт одразу за ним. Це класичне «на одиницю більше».

**Виправлення.** Перевірка меж лишається на місці в кожній точці, де адреса гостя перетворюється на індекс хоста: `set16` повертає `false`, `step` повертає помилку замість звернення до пам'яті (див. M2), оболонка відхиляє `addr >= MEM_SIZE` ще до виклику. Та сама ситуація, але в мові машини, дає не звіт ASan, а повідомлення й зупинку:

```
ember> set 0 0x28 0xFF 0x0F 0x29 0x2B 0x29 0x00   <- LOADH H,0x0FFF; LOAD A,[H]; INCH; LOAD A,[H]
ember> run
-- error: LOAD A,[H] at 0x1000: address out of range (valid 0x000..0xFFF)  (4 steps)
```

`H` дійшов до `0x1000` (за останню комірку) і машина зупинилась, а не прочитала чуже.

Увесь проєкт, включно з обома наборами тестів, зібрано й прогнано під `-fsanitize=address,undefined`: звітів немає. (Ця перевірка вже раз знайшла реальну помилку, у моєму ж тесті: поле `old` у допоміжній структурі ініціалізувалось через `sink` раніше, ніж `sink` створено. Порядок полів визначає порядок ініціалізації, а не список у конструкторі.)

## Самоперевірка

# З попередніх лаб (Lab 02)

Те, що лишилося від Lab 2 і не перекрите розділами вище. Рядок регістрів у трасуваннях нижче записано до появи `H`: тоді він мав вигляд `PC A B Z N C`, тепер у ньому ще й `H`.

## Розбір опкода масками

Старший півбайт опкода — це група, тому `decode` не тримає таблицю магічних чисел:

```cpp
Decoded decode(Byte op) {
    d.group = (op >> 4) & 0x0F;   // 0x1_ -> ALU
    d.index =  op       & 0x0F;
}
```

`step()` розводить `switch` за `decode(op).group`: група `0x0` іде в керування, група `0x1` у `exec_alu`.

## Розібрані приклади: загортання і перенесення

**1. `200 + 100`.** 200 = `1100 1000`, 100 = `0110 0100`. Сума 300 = 256 + 44 не влізла у вісім бітів: молодші вісім дають `0010 1100` = 44, а дев'ятий біт виїхав у `C`.

```
alu add 200 100   ->   result=44  Z=0 N=0 C=1
```

**2. `5 - 10` (позика).** Менше віднімають від більшого, тож результат загортається: 5 − 10 = −5 ≡ 251 (`1111 1011`). Старший біт одиниця, тому `N=1`; позика виставляє `C=1`.

```
alu sub 5 10      ->   result=251  Z=0 N=1 C=1
```

Ще два випадки, які перевіряє `alu`:

```
alu add 255 1     ->   result=0    Z=1 N=0 C=1     (загортання в нуль)
alu shl 129       ->   result=2    Z=0 N=0 C=1     (біт 7 виїхав у C)
```

## Трасування

Формат кожного кроку: рядок `адреса: байт мнемоніка` і нові регістри після нього.

**M2: `ADD`, `HALT` при `A=200`, `B=100`** (байти `10 00` покладено через `set 0 0x10 0x00`):

```
0000: 10  ADD A, B
PC=0x0001  A=44 (0x2c)  B=100 (0x64)  Z=0 N=0 C=1
0001: 00  HALT
PC=0x0002  A=44 (0x2c)  B=100 (0x64)  Z=0 N=0 C=1
halted                      <- третій step відмовляє
```

**M3: `AND`, `HALT` при `A=7`, `B=1`:**

```
0000: 12  AND A, B
PC=0x0001  A=1 (0x01)  B=1 (0x01)  Z=0 N=0 C=0
0001: 00  HALT
PC=0x0002  A=1 (0x01)  B=1 (0x01)  Z=0 N=0 C=0
```

Маска `7 & 1` лишає тільки молодший біт, а `C` скинуто, бо `AND` завжди пише `C=0`.

**M3: `SHL` тричі, потім `HALT` при `A=0x30`** (байти `16 16 16 00`). Біт `0011 0000` їде вгору, поки не вилізе за край:

```
0000: 16  SHL A
PC=0x0001  A=96 (0x60)   B=0 (0x00)  Z=0 N=0 C=0
0001: 16  SHL A
PC=0x0002  A=192 (0xc0)  B=0 (0x00)  Z=0 N=1 C=0      <- старший біт став 1: N
0002: 16  SHL A
PC=0x0003  A=128 (0x80)  B=0 (0x00)  Z=0 N=1 C=1      <- біт виїхав за межу: C
0003: 00  HALT
PC=0x0004  A=128 (0x80)  B=0 (0x00)  Z=0 N=1 C=1
```

**`INC` не чіпає `C`:** `ADD` при `A=255`, `B=1` дає `A=0`, `Z=1`, `C=1`; наступний `INC` робить `A=1`, `Z=0`, але `C` лишається 1:

```
0000: 10  ADD A, B
PC=0x0001  A=0 (0x00)  B=1 (0x01)  Z=1 N=0 C=1
0001: 18  INC A
PC=0x0002  A=1 (0x01)  B=1 (0x01)  Z=0 N=0 C=1
```

## Баг із пріоритетом, який я показав навмисно

`==` зв'язує тісніше за `&`, тому `x & 1 == 0` — це `x & (1 == 0)`, тобто `x & 0`. З `-Werror` це навіть не збирається:

```
error: suggest parentheses around comparison in operand of '&' [-Werror=parentheses]
```

Без `-Werror` при `x = 2` вийшло:

```
x & 1 == 0      ->  0      (це 2 & 0)
(x & 1) == 0    ->  1      (2 парне)
```

Тому скрізь, де потрібна перевірка біта, стоять дужки: `(flags & mask) != 0`.
